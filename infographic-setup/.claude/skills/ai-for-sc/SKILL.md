# AI for Supply Chain

Build an inspectable workflow for a real supply-chain job. Put the decision and practitioner value before the tool.

## Start with the Creative Genome

1. Define the role, recurring task, decision, stakes, current friction, desired artifact, and human owner.
2. Read `references/creative-genome/active-manifest.json` and create `data/{week}/{slug}/reference-query.json`.
3. Retrieve positive saved-post elements plus relevant Tiger precedents. Treat saved membership as validated creative taste; use Tiger outcomes to understand transfer to this account.
4. Inspect shortlisted visuals directly.
5. Build `reference-bundle.json` with two to four curated references plus separate Tiger precedents when useful. Select mechanisms for the opening, visual structure, explanation, save utility, and artifact bridge.
6. State how each mechanism changes for Shetty's Desk. Do not copy phrases, branding, claims, or creator CTAs.

Do not choose from a fixed hook taxonomy, force a tool rotation, or use a universal score. Let the reader decision and reference bundle determine the package.

## Route the claims

Run `research-engine ai-for-sc {slug}` for current tool capabilities and any factual, numerical,
comparative, or outcome claims. Require:

- current official sources for product surfaces, access, connectors, controls, and rollout status;
- authoritative domain methods, formulas, fields, and decision criteria when the workflow uses them;
- real public evidence for any claimed deployment, outcome, comparison, or savings;
- a clear separation between what the tool prepares and what the practitioner approves.

A proposed workflow does not require a documented company deployment when it makes no deployment or
outcome claim. Start public resources with public/licensed data, blank user input, or a no-data
walkthrough. Use simulation only when explicitly selected and labelled; never present it as proof.

## Design the workflow

Specify only the layers the use case needs:

1. Input pack and source systems.
2. Persistent method such as a skill, agent, governed instruction, script, or workflow.
3. Connected context and permitted actions.
4. Deterministic calculations or transformations.
5. Validation that can reject, block, or route unsupported output.
6. Finished artifact for the real meeting or task.
7. Trigger or cadence when recurrence matters.
8. Named human owner and system-of-record boundary.

Verify every named capability at the time of writing. Do not turn ordinary chat into a flagship workflow claim.

## Build the post and artifact

1. Write the care statement: `For [role] in [moment], this helps them [understand, decide, or act] because [reason it matters].`
2. Open with the operating problem, documented result, or consequential distinction. Mention the tool first only when the product change is the actual news.
3. Explain the workflow with connected reasoning and enough detail to inspect it.
4. Show the input, control, output, owner, and meeting payoff.
5. Apply `tiger-voice.md` and the approved `tiger-source.md`. Do not invent first-person use, results, clients, or employers.
6. Use `layout-select` to translate the bundle into one primary visual argument.
7. Use exact logos, product names, figures, and labels. Use deterministic overlays or HTML when generation could change them.

## Resource and handoff

Build a downloadable resource only when it lets the reader perform or inspect the real workflow. Separate internal safe-test fixtures from public evidence. Record limitations, controls, validation, version, and human ownership.

Require explicit approval for the caption and still before website handoff. Apply the existing motion gate only after `visual.png` is approved; keep `gif-storyboard` unchanged.

## Stop conditions

Stop when a claimed capability is not current and official, a claimed outcome lacks real support, the
workflow has no rejection control, simulation is disguised as proof, the artifact does not improve a
real task, or required Tiger authority is unapproved.
